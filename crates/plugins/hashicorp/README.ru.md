# Плагин HashiCorp Vault

**Языки:** [English](README.md) · Русский

Это руководство относится к `crates/plugins/hashicorp/` и описывает только данную интеграцию. Архитектура общего аккаунта, daemon, зашифрованного vault и границы плагинов описана в [руководстве ядра](../../../docs/core/README.ru.md).

## Назначение

Плагин — клиент Vault и broker краткоживущего доступа. Он может работать с одним выбранным Vault за раз (подключений можно сохранить несколько), проверять состояние/запечатанность, выполнять unseal, bootstrap/manage root token, выпускать и отзывать Vault-токены, просматривать/управлять policies, подключать/отключать/настраивать secrets engines и auth methods, работать с KV secrets и их версиями. Это не backend Bitwarden/Vaultwarden, а интеграция с отдельным сервисом HashiCorp Vault.

Плагин устанавливается как отдельный исполняемый файл. Включите HashiCorp Vault в Настройки → Плагины после просмотра разрешений. Его интерфейс отображает окно Keyward, а сетевые операции выполняются в процессе плагина.

## Поля подключения: зачем `kw-*`

Подключение Vault представлено custom fields обычной записи в vault. Namespace `kw-` явно обозначает принадлежность поля интеграции, предотвращает случайные совпадения с пользовательскими полями, синхронизирует настройки вместе с записью и не протаскивает интеграционную схему в универсальное ядро. Это по-прежнему поля зашифрованной записи на Bitwarden-совместимом сервере; отдельную plaintext-базу credentials плагин не заводит.

| Поле | Назначение |
|---|---|
| `kw-vault-addr` | Base URL Vault; идентифицирует и находит подключение. |
| `kw-vault-role-id` | AppRole `role_id`. |
| `kw-vault-secret-id` | AppRole `secret_id`; храните как защищённое custom field. |
| `kw-vault-namespace` | Необязательный Enterprise namespace. |
| `kw-vault-token` | Управляемый root token в скрытой служебной записи конкретного Vault; используется для аутентификации, если AppRole недоступен. Защищайте как секрет. |
| `kw-vault-unseal-fields` | Имена custom fields с Shamir shares через запятую. Хранятся имена, а не вторая копия значений. |
| `kw-issued` | Журнал выдач в скрытой служебной записи Vault; содержит accessors и метаданные, но не значения выданных токенов. |
| `kw-root-addr`, `kw-root-issued`, `kw-root-revoked` | Метаданные записи/жизненного цикла управляемого root token. |
| `kw-hidden` | UI-маркер скрытой служебной записи Keyward; она синхронизируется как обычный vault item и может быть видна в веб-интерфейсе Bitwarden/Vaultwarden. |

В интерфейсе укажите обычную заметку для подключения и выберите имена существующих полей с unseal shares. Предпочитайте этот процесс ручному заполнению служебных метаданных. При permission `secrets` плагин самостоятельно читает только поля с префиксом `kw-`. Gate проверяет префикс, но не владельца-плагин и не защищённый тип поля; считайте `secrets` доступом ко всем значениям `kw-*`. Для выбранных share fields без этого префикса окно читает значения в явно запущенном пользователем процессе unseal/генерации root token и передаёт их операции; плагин не может читать такие поля в фоне.

Root token и журнал выдач находятся в отдельной скрытой **личной/принадлежащей пользователю** служебной записи для каждого Vault, а не в заметке подключения и не в общей записи организации. Плагин игнорирует hidden item, который не принадлежит текущему пользователю: это не позволяет участнику организации подложить похожий журнал или записать root token в общую заметку. Hidden-маркер действует только в списках Keyward; в web vault сервера запись остаётся обычной secure note.

## Подключение и unseal

1. Откройте **HashiCorp Vault** в навигации плагинов Keyward и выберите **Connect**.
2. Введите URL Vault. Перед сохранением плагин проверяет endpoint.
3. Выберите существующую обычную заметку/запись vault или создайте новую для метаданных подключения; при Shamir укажите имена существующих полей с shares. Плагин сохраняет имена, а не копирует значения отдельно.
4. Настройте AppRole `role_id` и `secret_id`, а при необходимости namespace. Если AppRole не задан и управляемый root token существует, broker может аутентифицироваться токеном из скрытой записи. Для регулярной работы предпочтителен ограниченный AppRole.
5. Если сервер sealed, передайте лишь число shares, нужное для достижения порога. Генерация root token — отдельная церемония высокого риска: shares передаются операции на стороне daemon, а готовый токен записывается в отдельную скрытую служебную запись, а не отображается обычным текстом на экране.
6. Выберите подключение активным. Broker работает с ним; выбор другого переключает активный Vault.

Unseal shares — мощные credentials. Не помещайте их в аргументы команд, git, скриншоты или обычные логи. Не используйте root token для повседневных задач.

## Broker токенов: выдача, передача, аудит, отзыв

В консоли Vault откройте **Issued access**/выдачу доступа. Запрос содержит категорию получателя (agent, person или self), policies, TTL, необязательный лимит использований, wrapping и заметку. В UI доступны TTL 5m, 15m, 30m, 1h, 4h и 24h. Значения по умолчанию: 15 минут для agent, 1 час для person, 30 минут для self; перед выпуском проверьте фактический запрос. Нулевой лимит использований означает неограниченное число, а не однократное использование.

Vault выдаёт обычный token или, при wrapping, одноразовый wrapping token. Его нужно один раз обменять через Vault unwrap; если он уже использован, считайте его перехваченным, отзовите/перевыпустите доступ. Не задавайте wrapping token как `VAULT_TOKEN`, будто это финальный credential.

Журнал хранит **accessor**, категорию/заметку, policies, TTL и состояние — но не bearer token. Accessor позволяет отозвать токен, не сохраняя сам токен. Активную выдачу можно отозвать из UI; при обновлении/tick истечения отмечаются автоматически, а при включённых уведомлениях плагин сообщает незадолго до конца (в пределах двух минут) и при истечении. Выданное значение копируется через clipboard capability ядра, которая помечает буфер как содержащий секрет и очищает его по настройке приложения.

Для привилегированных policies `root`/`sudo` и специальной broker policy `keyward-policy-admin` требуется отдельное согласие «wide access»; действуют защитные ограничения плагина (root-эквивалентный token ограничен максимумом в один час). Используйте минимальные policies, минимальный практически достаточный TTL и узкую область доступа. Специальная policy `keyward-policy-admin` сохраняется только пока активный выданный Keyward token в ней нуждается; автоматическая очистка не заменяет ревизию policies и отзыв credentials.

## Policies и engines

Консоль умеет перечислять/читать/создавать/удалять ACL policies и просматривать, монтировать, отключать и настраивать secrets engines и auth methods. Настройки mount включают описание и default/max lease TTL. Для KV доступны v1/v2; UI показывает параметры KV v2, например `max_versions`, `cas_required`, `delete_version_after`. Переход KV v1→v2 необратим; пути policy отличаются (`data/` и `metadata/` в v2), поэтому до изменения проверьте policies и эффект миграции.

Пути mount и типы движков валидируются. Не отключайте auth method или engine без оценки последствий: могут измениться способы входа, доступность данных и зависимые policies. Точные типы engine/auth зависят от сервера Vault и версии плагина.

## KV secrets и версии

Плагин просматривает KV mounts, перечисляет пути, читает выбранный секрет, копирует отдельные значения, создаёт/обновляет запись и меняет метаданные. Для KV v2 доступны история версий, восстановление старой версии записью её данных как новой текущей версии, undelete soft-deleted version, необратимое уничтожение версии и изменение метаданных конкретного секрета. При поддержке используется Check-And-Set, чтобы уменьшить риск затереть параллельные изменения.

Значения не включаются в обычный список/детали: интерфейс показывает имена ключей и длины значений и получает конкретное значение только при просмотре/копировании или редактировании. Копирование проходит через clipboard core. Удаление может быть soft либо permanent, если это различает engine. Необратимое уничтожение, изменение metadata и редактирование policy имеют высокий эффект; внимательно сверяйте mount/path/version и preview подтверждения.

## Встроенные permissions и доверие

Manifest запрашивает `entries`, `items`, `items_write`, `secrets`, `notices`, `network`, `clipboard`. Они нужны, чтобы находить собственные помеченные записи подключения/сервиса, читать карточки и поля, менять метаданные плагина, читать защищённые credentials плагина, сообщать об истечении, обращаться по сети к Vault и копировать результат. `network` — явно раскрываемое разрешение, но не сетевая песочница ОС.

Данные подключения и журнал выдач хранятся в записях vault; выбранное активное подключение и настройки уведомлений — в settings плагина. Запись root token скрыта. Защищайте Mac и доступ к vault. Само раскрытие журнала не должно давать пригодный bearer token, но плагин имеет полномочия обращаться к Vault с настроенными credentials.

## Ограничения и безопасная эксплуатация

- В каждый момент активно одно подключение Vault.
- Это инфраструктурное администрирование: начните с тестового Vault и least-privilege policies.
- Root tokens и unseal shares способны дать полный контроль Vault; минимизируйте их время жизни и раскрытие.
- Короткий TTL ограничивает время действия credential, но не его полномочия, пока он действителен.
- Очистка clipboard и уведомления уменьшают экспозицию, но не делают безопасной вставку токена в недоверенный процесс.
- Проект экспериментальный, независимого аудита нет. Проверьте именно ту сборку плагина и поведение API/edition Vault, которые разворачиваете.
