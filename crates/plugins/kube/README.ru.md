# Kubernetes-плагин

**Языки:** [English](README.md) · Русский

Это руководство принадлежит `crates/plugins/kube/` и описывает поведение Kubernetes. Общее устройство Keyward изложено в [руководстве core](../../../docs/core/README.ru.md). Функция экспериментальная и не заменяет `kubectl`.

## Источники кластеров и владение `kw-*`

Плагин использует Kubernetes kubeconfig из заметки vault либо находит кластер на сервере, доступном по SSH. Обнаружение через облачные провайдеры (EKS и другие) обозначено как будущая работа, а не действующий источник.

### Kubeconfig в vault

Создайте защищённую заметку с custom field **`kw-kubeconfig`**. Префикс показывает, что поле принадлежит схеме этого плагина, не даёт перепутать его с несвязанным пользовательским полем `config` и сохраняет конфигурацию на зашифрованной записи-владельце. Неиспользуемые контексты импортированного файла удаляются; выбирается один current/явно заданный контекст и показывается до подключения. Можно импортировать `~/.kube/config` или вставить YAML размером до 256 KiB. При локальном импорте файлы сертификатов/ключей/token, на которые ссылается kubeconfig, читаются и встраиваются в выбранный контекст, чтобы заметка была самодостаточной; поле нужно защитить, потому что в нём могут быть credentials и приватный ключ.

### Кластер, найденный по SSH

Плагин сканирует SSH-назначения, представленные записями vault. Он непосредственно использует общую SSH-библиотеку; включать отдельный экран SSH-плагина не требуется. Запись-источник должна иметь корректный маршрут `kw-host`, возможность SSH signing и доверенный host key. Соглашения маршрутов и known-host принадлежат [руководству SSH-плагина](../ssh/README.ru.md). Во время сканирования отправляется явная SSH-команда для поиска вероятной конфигурации control plane. Фоновый scan не выполняется: пользователь запускает полный scan или проверку одного сервера, затем открывает найденный кластер для чтения kubeconfig. В настройках плагина запоминаются только метаданные/статус обнаружения (адрес, тип кластера, результат, нужен ли sudo); kubeconfig считывается на время открытой сессии, хранится в памяти и не записывается отдельной локальной копией.

Отпечаток хоста показывается до явного trust. Ошибки входа, неизвестный/изменившийся host key или отказ сервера выполнить detection-команду отображаются как failure/unknown; SSH-хост, принимающий команды только своего назначения, не считается кластером.

## Выбор kubeconfig и защитные проверки

Плагин сужает файл до выбранного context, связанного cluster и связанного user; другие contexts/auth entries не передаются Kubernetes-клиенту. Перед созданием клиента запрещаются:

- API endpoint без HTTPS и TLS `insecure-skip-tls-verify`;
- proxy URL;
- kubeconfig `exec` plugins и старый `auth-provider` (никакого запуска произвольных программ на Mac);
- неподдерживаемые пути файлов remote-конфигурации. Для remote источника ссылки на CA/cert/key/token читаются на удалённом хосте и встраиваются; путь, пришедший с сервера, никогда не трактуется как путь к файлу на Mac пользователя.

К API обращаются через соответствующий источник: напрямую по HTTPS для local kubeconfig либо через SSH tunnel плагина для найденного по SSH кластера. Namespace контекста используется по умолчанию; в UI можно выбрать другой. Credentials остаются в памяти открытой сессии кластера; закрывайте её и блокируйте vault после работы.

## Что доступно для просмотра

Поддерживаемые типы: Namespaces, Nodes, Pods, Deployments, StatefulSets, DaemonSets, Services, Ingresses, ConfigMaps, Secrets, Events, Roles, RoleBindings, ClusterRoles, ClusterRoleBindings и NetworkPolicies. Namespaced-типы можно просматривать в namespace или по всем namespace; cluster-scoped типы отображаются на уровне кластера.

Списки специально сведены к рабочим показателям (например, фаза/readiness/restarts/node pod, готовые и желаемые реплики, service ports, ingress hosts, reason/message events и количество правил/участников RBAC), а не являются универсальным YAML dump. **Значения Kubernetes Secret не перечисляются и не открываются:** Keyward запрашивает только metadata и запрещает показывать manifest Secret. Это ограничение сохраняется даже при широком RBAC у kubeconfig.

Для поддерживаемых non-Secret ресурсов интерфейс может показывать object/manifest, редактировать YAML, создавать из формы/template, применять изменения, удалять объекты, масштабировать workloads, перезапускать поддерживаемые workloads, читать логи pod/container и открывать интерактивный shell в pod/container. Фактический доступ зависит от API и RBAC выбранной identity. Shell выполняется внутри контейнера со служебной identity, сетью и файловой системой контейнера; это не отдельная песочница Keyward.

Перед изменением используется server-side dry-run API: UI показывает вычисленное изменение и состояние до/после. Изменений нет, пока пользователь не подтвердит реальное применение. Перепроверьте diff/manifest, namespace и имя объекта. Удаление, scale, restart, shell и apply способны влиять на production. Keyward не повышает Kubernetes RBAC.

## Подключение и работа

1. Разблокируйте vault и откройте Kubernetes.
2. Добавьте kubeconfig: импортируйте локальный `~/.kube/config`, вставьте YAML либо просканируйте серверы, доступные по SSH. Для SSH проверьте fingerprint и разрешите именно ожидаемый хост; подтвердите необходимое действие пользователя/signing.
3. Выберите/подтвердите context. Проверьте API URL и namespace; другие contexts исходного файла не считаются подключёнными.
4. Откройте cluster для API-сессии. Просматривайте namespace/resources; изменение выполняйте только после проверки preview.
5. Завершив работу, закройте сессию кластера и заблокируйте vault.

Сканирование SSH-хоста — осмысленное действие: оно входит на сервер, может выполнить read-only discovery script и потребовать sudo. Не подтверждайте host/user prompt, который вы не инициировали. Таймауты ограничены: до 20 секунд на поиск/чтение и на каждый API request.

## Permissions, состояние и приватность

Manifest заявляет `entries`, `items`, `items_write`, `secrets`, `notices`, `ssh_sign`, `network`. Это нужно для поиска vault entries/configuration, чтения карточек, импорта заметки kubeconfig, доступа к защищённому полю, уведомлений, SSH signing через core и подключения к Kubernetes/SSH endpoint. `clipboard` не запрашивается.

Результаты обнаружения — несекретные настройки плагина. Kubeconfig/credentials не сохраняются отдельным локальным cache после импорта/открытия. Сеть заявлена в manifest, но не песочница ОС на уровне core. Последнее слово — Kubernetes RBAC: используйте отдельную минимально привилегированную identity вместо cluster-admin и проверьте доступ, который даёт выбранный context.

## Известные границы

- SSH — единственный активный источник удалённого обнаружения; облачные managed-provider источники относятся к будущей работе.
- `exec`, `auth-provider`, proxy URL, обычный HTTP и пропуск проверки TLS запрещены.
- Это консоль выбранного набора ресурсов; она не открывает любой API kind или произвольные расширения Kubernetes.
- Payload/manifest Kubernetes Secret намеренно недоступен.
- Проект экспериментальный и не аудирован; проверьте всё на непроизводственном кластере до включения мутаций.
