# Ядро Keyward: архитектура и руководство пользователя

**Языки:** [English](README.md) · Русский

Документ описывает общее ядро Keyward. Он намеренно **не описывает поведение отдельных интеграций**: руководства по ним находятся рядом с исходниками в [`crates/plugins/`](../../crates/plugins/). Полная [карта документации](../README.md).

## 1. Граница продукта

Ядро Keyward — локальный клиент Bitwarden-совместимого хранилища: настройка учётной записи, аутентификация, синхронизация зашифрованного vault, разблокировка/блокировка, просмотр и редактирование записей, настройки приложения и доверенный локальный канал управления. Нативное окно macOS и CLI обращаются к пользовательскому daemon. Поведение конкретных интеграций вынесено в отдельно документированные компоненты; ядро не должно знать их маршруты, схемы полей или рабочие процессы.

README проекта перечисляет Bitwarden cloud, Vaultwarden и совместимые с Bitwarden-протоколом серверы. Первая нативная цель — macOS 14+ на Apple silicon. Программа экспериментальная и не проходила независимый аудит.

## 2. Выполнение и движение данных

```text
окно macOS / CLI ── аутентифицированный зашифрованный локальный канал ──► daemon
                                                                        │
                                                                        ├── учётная запись, сессия и криптография vault
                                                                        ├── HTTPS API ──► Bitwarden-совместимый сервер
                                                                        └── Host boundary с проверкой capabilities ──► интеграции
```

Daemon владеет ключами разблокированного хранилища и является источником истины для состояния vault. GUI отображает данные и собирает намерения пользователя, но не создаёт второго владельца расшифрованного состояния. CLI проходит через ту же локальную границу. После установки пользовательский LaunchAgent запускает daemon.

Сервер хранит записи в зашифрованном формате Bitwarden. Keyward аутентифицируется, выводит/разблокирует ключи, синхронизирует зашифрованный снимок и расшифровывает записи локально для использования. Локальные данные сессии и удалённый зашифрованный снимок — разные сущности: снимок является ciphertext, а сессия содержит данные аутентификации и ключей и локально запечатывается. Имена account-файлов хешируются, а не раскрывают идентификатор. Чувствительные локальные файлы создаются с ограниченными правами и атомарной заменой там, где это реализовано. См. [`crates/core/src/paths.rs`](../../crates/core/src/paths.rs), [`crates/vault/`](../../crates/vault/) и [`crates/bw/`](../../crates/bw/).

Блокировка — это переход безопасности, а не просто скрытие окна: daemon удаляет ключи разблокированного vault из памяти и посылает событие `locked`. Зависимые живые возможности должны остановить сессии/сокеты и очистить копии данных. Для дальнейшей работы нужно снова разблокировать vault. В настройках задаются тайм-аут блокировки, действие lock/logout, Touch ID и очистка буфера.

## 3. Записи и пользовательские поля

Keyward сохраняет совместимую с Bitwarden модель элементов, а не вводит отдельную серверную схему. Обычные пользовательские данные принадлежат пользователю. Имя custom field — плохое место, чтобы интеграция молча присвоила себе произвольные поля; поэтому используется явное соглашение о пространстве имён: **`kw-`**.

Зачем нужен этот префикс:

1. **Владелец семантики виден по соглашению.** `kw-host` или `kw-vault-addr` сообщает, что смысл поля определяет компонент Keyward. Пользовательское поле `environment`, `host` или `token` случайно не будет истолковано как настройка интеграции.
2. **Сохраняется совместимость со схемой сервера.** Это custom fields внутри обычных зашифрованных записей, а не новые колонки базы сервера и не параллельное хранилище секретов. Поля синхронизируются вместе с записью и остаются связаны с ней.
3. **Ядро остаётся универсальным.** Core не разбирает каждое имя `kw-*` и не должен знать, что такое SSH-маршрут, Vault-подключение или kubeconfig. Схему владеющего поля документирует и проверяет его компонент.
4. **Доступ ограничивается.** Внешний плагин может запросить значение custom field через `secret`, только если имя поля начинается с `kw-` (без учёта регистра); этим методом нельзя получить пароль, TOTP, приватный ключ или произвольное пользовательское поле. Важное уточнение: текущий gate проверяет только префикс — не владельца-плагин и не признак protected/hidden у самого поля. Владение полями отдельных плагинов — соглашение схемы и документации, а не технический ACL пространств имён. Плагин дополнительно должен объявить `secrets`, а каждый Host-метод проверяется по permissions. Записи проходят через явные методы host и требуют `items_write`.

Префикс — это **маркер пространства имён, а не криптографическая метка доверия, ACL плагина или проверка типа поля**: сам по себе он не делает значение секретным и не доказывает безопасность плагина. Gate чтения внешнего плагина не проверяет, помечено ли custom field как protected/hidden; для чувствительных значений используйте защищённый тип поля, а плагин с `secrets` считайте доверенным в отношении значений полей `kw-*`. К плагину с `secrets` и `network` нужно относиться особенно внимательно. Схемы конкретных полей находятся в руководствах плагинов; см. [индекс плагинов](../../crates/plugins/README.md).

Некоторые компоненты помечают служебные записи как hidden, чтобы они не загромождали обычные списки Keyward. Это соглашение интерфейса приложения, а не новая граница безопасности хранилища или сервера: запись синхронизируется как обычный элемент Bitwarden-совместимого vault и может быть видна в веб-интерфейсе самого сервера. Защищайте значение по его секретности, например root token, а не полагайтесь на маркер hidden.

## 4. Граница плагинов (контракт на уровне core)

Плагины — подключаемые возможности, а не второе ядро. У плагина есть идентификатор, manifest, объявленные permissions, настройки и описание интерфейса, которое отображает GUI. SSH, HashiCorp Vault, Kubernetes и Vaultwarden устанавливаются как отдельные исполняемые файлы и не загружаются в адресное пространство daemon. При первой установке они выключены: включите нужные интеграции в Настройки → Плагины после просмотра разрешений. Переустановка сохраняет их включённое или выключенное состояние.

Внешний пакет после установки выключен. Включение означает согласие с permissions из manifest; daemon проверяет каждый вызов Host-метода. Неизвестные методы запрещаются. Канал внешнего плагина в protocol v2 использует Noise handshake и аутентифицированное шифрование; перехода на plaintext нет. Это уменьшает неявное совместное использование полномочий, но не делает код автора доверенным.

Важный нюанс: `network` показывается как запрашиваемое разрешение, но core не может перехватить произвольные сетевые вызовы дочернего процесса. Это раскрытие намерения пользователю, а не сетевая песочница на уровне ОС. Связка `secrets` + `network` может вынести секреты с устройства. Полное описание протокола и упаковки: [протокол плагинов](../plugin-protocol.md) и [проверки каталога/установки](../plugin-registry.md).

## 5. Пользовательские процессы ядра

### Учётная запись

1. Настройте облачный регион либо self-hosted сервер и идентификатор аккаунта.
2. Войдите мастер-паролем и поддерживаемым вторым фактором, если сервер его запросит.
3. Разблокируйте vault в приложении. По желанию выполните `keyward remember`, чтобы проверить мастер-пароль и сохранить его под контролем macOS Keychain/user presence, а затем разблокировать через Touch ID.
4. При необходимости синхронизируйтесь. Уходя от компьютера, блокируйте vault: ключи выйдут из памяти, зависимые агентские сессии закроются.

Базовые команды CLI:

```sh
keyward setup --region self --url https://vault.example.com --email you@example.com
keyward login
keyward status
keyward sync
keyward lock
```

Точные параметры: `keyward --help` и `keyward setup --help`.

### Просмотр и редактирование

Нативное приложение показывает личное и организационные хранилища, списки с поиском и страницы записей. Поддерживаются логины, защищённые заметки, идентификаторы, карты и SSH-записи. Чувствительные значения маскируются до явного просмотра или копирования. В совместимой записи могут отображаться TOTP и passkeys. Верхняя строка одновременно навигационная: `⌘K` переводит в неё фокус; команды с `>` показывают предварительный план до выполнения.

Приложение включает генератор паролей, очистку буфера обмена, настройку иконок сайтов, языка/темы/акцентного цвета, меню-бар, вход при логине, действие тайм-аута lock/logout и настройки запросов Touch ID. Это локальные настройки поведения приложения, если явно не указано, что настройка принадлежит vault или сервисному компоненту.

### Passkeys в браузере

WebAuthn в Chromium использует отдельное расширение и локальный native-messaging host, а не плагин браузера, загруженный в core. Pairing подтверждается сравнением ключа пользователем; подпись и регистрация passkey одобряются Touch ID в приложении. См. [инструкцию и приватность расширения](../../extension/README.md) и [политику приватности](../extension-privacy.md).

## 6. Локальное состояние и границы доверия

По умолчанию данные приложения находятся в `~/.keyward` (в development/test можно задать `KEYWARD_HOME`). Там расположены настройки, список аккаунтов, данные сессий/снимков на аккаунт, данные доверия SSH-хостам, сокеты и состояние внешних плагинов. Не прикладывайте этот каталог к issue и не передавайте его без очистки. Точный набор файлов и форматы — детали реализации, они могут мигрировать между версиями.

Есть несколько разных границ доверия:

- **Vault-сервис:** получает трафик аутентификации/API и хранит ciphertext; протокол шифрования не передаёт ему разблокированные клиентские ключи.
- **Локальный Mac и аккаунт:** daemon, учётная запись ОС, Keychain и запущенные процессы находятся внутри локальной границы доверия.
- **Код Keyward:** приложение и daemon обрабатывают секреты локально; важны экспериментальный статус и отсутствие независимого аудита.
- **Внешние процессы интеграций:** доступ ограничивают permissions и конкретные Host-методы; запрошенный `network` не является OS-level сетевой песочницей.
- **Origin веб-клиента:** сервер развёртывания может подменить JavaScript. У браузерной версии отдельная модель угроз; см. [`web/README.md`](../../web/README.md).

## 7. Свойства защиты и известные пробелы

В проекте описаны такие меры, как запечатанный локальный канал daemon, зашифрованные pipe плагинов, локальная криптография vault, ограниченный доступ Keychain к запомненным credentials, очистка буфера обмена, удаление agent sockets при блокировке и отключённое сетевое логирование, чтобы credentials не попадали в traces. Поведение безопасности всё ещё экспериментальное; проверяйте именно используемую сборку/релиз.

Криптография vault реализована в Keyward поверх RustCrypto без зависимости от rbw. Поддерживаются аккаунты PBKDF2 и Argon2id и аутентифицированные симметричные ciphertext типа 2. Старый неаутентифицированный тип 0 и COSE типа 7 не поддерживаются. Полная двусторонняя проверка совместимости с официальным Bitwarden Desktop ещё не выполнена.

SSH поддерживает OpenSSH-ключи Ed25519, RSA и поддерживаемые ECDSA, проверку session binding в агенте хоста и явное подтверждение ключа сервера в терминале. Проверка pin агентом требует, чтобы клиент передавал session binding. Аппаратные ключи, proxy-jump и certificate-сессии терминала, выпуск Vault SSH-сертификатов не поддерживаются. Подробности — в руководстве SSH-плагина. Этот документ не является результатом аудита или сертификацией.

## 8. Разработка и тестовые свидетельства

```sh
npm ci
npm run build
cargo test --workspace --locked
cargo build -p keyward-cli --locked
./scripts/smoke.sh
node scripts/native-vault-contract.mjs
make run
```

Demo stand (`npm -w @keyward/stand run dev`) использует фиктивные фикстуры и не требует живого daemon/vault. Тесты имеют область действия: успешный suite не доказывает корректность каждого UI-сценария, операции сервиса, разрешения плагина, мутации или платформенного пути. Контракт мутаций web-клиента отдельно описывает покрытие и отложенные случаи в [`docs/state-mutation-contract.md`](../state-mutation-contract.md).

## 10. Сообщения о проблемах безопасности

Keyward работает с паролями и приватными ключами. О потенциальной уязвимости сообщайте приватно через GitHub **Security → Report a vulnerability**; не публикуйте детали эксплойта в открытом issue. См. [`SECURITY.md`](../../SECURITY.md).
